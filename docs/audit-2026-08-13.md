## 🔴 P1 — CE Lua bridge:`U.callDLL` 每一次呼叫都打錯位址 — ✅ FIXED(2026-08-13)

**[scripts/utils.lua:136](../scripts/utils.lua)**(`dist/utils.lua` 同步同病)

CE 的實際簽章(取自本機 `C:\Program Files\Cheat Engine\celua.txt:589`):

```
executeCodeEx(callmethod, timeout, address, {type=x,value=param1} or param1, ...)
```

`address` 是**第三個**位置參數。程式碼只給兩個:

```lua
local conv = (retType == "void") and 0 or 1
local ret  = executeCodeEx(conv, fn, ...)
```

→ `callmethod=conv`、**`timeout=fn`(把 export 位址當成逾時毫秒數)**、
**`address=` 第一個 vararg**(無參數時為 `nil`)。

**後果**:CE-table 分發路徑上,每一個 DLL export 呼叫都在呼叫錯誤位址 —— 無參數時位址是 `nil`,
有參數時把使用者傳的參數值當成程式碼位址跳過去(在遊戲行程內執行任意位址 → CTD)。
`Discrete_Init` / `Discrete_Shutdown` / 全部 bridge 控制流受影響。

**第二個缺陷(同一行)**:`callmethod` 的語意也理解錯了。celua.txt:590 寫明
**`0=stdcall, 1=cdecl`**,與回傳型別無關;原碼卻用 `(retType == "void") and 0 or 1`
依回傳型別在兩種呼叫慣例間跳動。exports 宣告為 `extern "C" __declspec(dllexport)`
無顯式慣例 → MSVC 給 `__cdecl` → 應恆為 `1`(32-bit Mono build 上有實質差異;x64 只有單一慣例)。

**已修**:`executeCodeEx(1, nil, fn, ...)`,`scripts/utils.lua` + `dist/utils.lua` 兩份同步。
`timeout=nil` = 無限等待,對應原本的阻塞語意;celua.txt:591 註明 `timeout=0` 會讓 CE
不釋放 call stub(每次呼叫洩漏),故不採用。

> ⚠️ 修正只在 **UI 重新 build** 後才進到 `UnityDumpUI.Core.dll`
> (`scripts/*.lua` 經 `<EmbeddedResource Include="..\..\scripts\utils.lua">` 內嵌)。
> `dist/*.lua` 已直接更新,手動組 CE table 的路徑立即生效。**待實機 smoke**。

## 🔴 P2 — ScanCancel 陳舊旗標污染 → reverse-lookup index 靜默截斷並發佈進全域快取 — ✅ FIXED(2026-08-13,build #1382)

**[dll/src/shared/ScanCancel.h:46](../dll/src/shared/ScanCancel.h)** +
**[dll/src/mono/MonoAddressFinder.cpp:1228](../dll/src/mono/MonoAddressFinder.cpp)**
(IL2CPP 孿生:[IL2CPPAddressFinder.cpp:1396](../dll/src/il2cpp/IL2CPPAddressFinder.cpp))

四個獨立 finder 各自撞到,人工追完整條鏈:

1. `Scope` 解構子(ScanCancel.h:46-48)只清 `g_scanActive`,**不清 `g_scanCancel`**。
   旗標只在**下一個** `Scope` 建構子(:43)才被清掉。
2. 但只有 4 個 handler 開 Scope(ExportAPI.cpp:5909 / 6089 / 9382 / 9559 =
   `beginValueScan` / `beginGroupScan` × 兩 backend)。
   **`CmdScanFieldValue`(ExportAPI.cpp:5506,下一個 handler 在 5904)沒有 Scope**,
   卻在 :5824 呼叫 `revIndex.Build()`。
3. 使用者取消一次 value scan 後 `g_scanCancel` 永久為 true;接著跑 **Scan field value** →
   `MonoAddressFinder.cpp:1163` `if (IsCancelRequested()) break;` **在第一個 region 就跳出** → index 幾乎是空的。
4. `Build` 不檢查是否被取消,照樣排序、log、**發佈進 process-wide reuse cache
   並標 `c.valid = true`、`return true`**(MonoAddressFinder.cpp:1228-1233)。
5. 呼叫端 `revIndexOk == true` → 每次 `Lookup()` 都 miss → **結果靜默錯誤/空白**,無任何錯誤訊息。
6. 快取蓋上 `builtAtTick`,在 reuse window 內被後續呼叫複製 —— 連之後有清旗標的 scan 也會拿到被污染的 bases。

**現存證據顯示開發者已知旗標會殘留**:ExportAPI.cpp:2330-2338 的註解明講
「STALE `g_scanCancel`(armed by a previously-cancelled scan and only cleared by the NEXT begin\* Scope)」,
但只在 `refineGroupScan` 一處用「不 poll」規避,沒有從根源清掉。

### 已修(兩層:根因 + 安全網)

**① 根因 —— [ScanCancel.h](../dll/src/shared/ScanCancel.h) `Scope::~Scope()` 一併清 `g_scanCancel`**,
讓旗標生命週期嚴格等於擁有它的 scan。**清除順序刻意是先 `active` 後 `cancel`** ——
`RequestCancel()` 的 gate 是 `g_scanActive`,先關閘門可縮小「清完又被晚到的 cancel 重新武裝」的視窗。

驗證過不會破壞既有語意:四個 handler 的 `Scope` 都是 handler lambda 的區域變數
(ExportAPI.cpp:5909 / 6089 / 9382 / 9559),而回應階段的
`if (IsCancelRequested()) return {"cancelled": true}`(:6024 等)都在 lambda **內**,
解構子要等 handler return 後才跑 —— 取消回報照常運作。

**② 安全網 —— 兩個 backend 的 `ReverseLookupIndex::Build` 不再發佈被取消的索引**
([MonoAddressFinder.cpp](../dll/src/mono/MonoAddressFinder.cpp) sort 前 /
[IL2CPPAddressFinder.cpp](../dll/src/il2cpp/IL2CPPAddressFinder.cpp) 合併 perThread 前):
偵測到取消就 `bases_.clear()` + `return false` + log,**完全不碰 reuse cache**。
呼叫端 `revIndexOk=false` → 走較慢但正確的 direct backward scan。
這層獨立於 ①,即使未來又有人在沒有 Scope 的路徑上呼叫 `Build`,也不會再污染快取。

**③ 順手修正 [ExportAPI.cpp:2329](../dll/src/shared/ExportAPI.cpp) 的過時註解** ——
它原本以「旗標只會被下一個 begin\* Scope 清掉」為由說明為何不 poll。該前提已不成立,
留著會誤導後人。改為保留「不 poll」的真正理由(early-break 會讓 `cands.resize(0)` 清空整個 session),
並註明歷史脈絡已由 ① 解決。

**驗證**:`build.cmd dll` SUCCESS(build #1382,x64 + x86 雙 backend + IL2CPP);UI 1123 tests 全綠。
**待實機 smoke**:跑一次 value scan → 中途 Cancel → 接著跑 **Scan field value**,
確認結果正確(修正前會靜默回空/錯誤結果)。

## 🟠 P3 — CE Lua bridge:`is32bitProcess()` 在 Cheat Engine 不存在 — ✅ FIXED(2026-08-13)

**[scripts/utils.lua:211](../scripts/utils.lua)**

```lua
local x86 = (is32bitProcess and is32bitProcess()) or false
if backend == "Mono" and x86 then return "Discrete-Mono-x86.dll" end
```

本機 `celua.txt` 只有 `targetIs64Bit()`(:712),**沒有 `is32bitProcess`**。
全域查找為 `nil` → `and` 短路 → `x86` 恆為 `false` → **32-bit Mono 遊戲永遠拿到 x64 DLL**。
注入失敗或載入錯誤位元的 DLL。因為寫成 `(fn and fn())` 的防禦形式,失敗是靜默的。

**已修**:`local x86 = (targetIs64Bit and not targetIs64Bit()) or false`。
注意**不能**用 `targetIsX86()` —— celua.txt:713 的語意是「架構家族」,x64 目標也回 true。

**同族一併修掉**:`ce_table_bootstrap.lua` 的 `_is32bit()`(scripts + dist)有完全相同的
不存在-API 問題,只是包了一層 `if is32bitProcess then ... end` 的假 fallback 讓它靜默回 false。
留著等於只修一半。

**`Discrete-Mono-x86.dll` 檔名已確認正確**:`dist/x86/` 產出的是 `Discrete-Mono.dll`,
但 [ce-bridge-integration.md:126-137](ce-bridge-integration.md) 說明組 CE table 資料夾時
**由使用者手動改名**成 `Discrete-Mono-x86.dll`(讓 x64/x86 兩份能並存於 .CT 旁同一資料夾)。
lua 端維持原樣。**待實機 smoke**:需要一款 32-bit Mono 遊戲驗證這條路徑現在真的會選 x86 DLL。

而它們講的是早已演進過的 pipe 協定。

**建議**:刪除 `dist/unity_addrfind.lua`、`dist/unity_dissect.lua`、`dist/unity_scene.lua`;
或讓 build.ps1 在複製前先修剪 `dist/*.lua` 中不存在於 `scripts/` 的檔案。

## 批次 A — ForegroundHook(完成 2026-08-13,build #1385)

人工逐行讀完 [ForegroundHook.cpp](../dll/src/shared/ForegroundHook.cpp)(324 行),零 agent。
**三項全部 CONFIRMED,且全部出自 audit #3 的 P4 修正本身(commit `06806c6`)** ——
正是「修正引入新缺陷」這一類,也是當初把它排第一批的理由。

### A-1(= F0 = F14)🔴 `RemovePropW` 無條件執行 → 外部 subclass 存在時永久繞過遊戲 WndProc — ✅ FIXED

`UnsubclassEnumProc` 的 WNDPROC 還原只在 `cur == &SubclassProc` 時做,但 `RemovePropW` 在分支**外面**,
無條件執行。當有外部模組(CE 自己、Steam/Discord overlay、RTSS、輔助工具)在我們之上再 subclass,
`&SubclassProc` 仍留在 chain 中卻失去了 prop:

```c
auto orig = GetPropW(h, kOrigProcProp);   // → nullptr
if (orig) return CallWindowProcW(orig, ...);
return DefWindowProcW(h, msg, w, l);       // ← 遊戲真正的 WndProc 被永久繞過
```

原註解「residual pass-through is already gated off by `g_enabled`」的推理是錯的:
`g_enabled` 只 gate 訊息改寫區塊,轉發那一行**不受 gate**,永遠執行。
拿掉 prop 不是讓 `SubclassProc` 變無害,是讓它變成吞掉原 WndProc 的黑洞
→ 輸入失效 / 繪製異常 / 視窗關不掉。

**修法**:無法還原時**保留 prop**(讓 `SubclassProc` 仍能轉發)並記 log;
`RemovePropW` 移進「確實已還原」的分支。代價是這種情況下模組不可 unload —— 已在 log 明說。

### A-2(= F1)🟠 `UnsubclassEnumProc` 缺少 process 過濾 — ✅ FIXED

兩個姊妹 callback(`PickLargestProc`、`SubclassEnumProc`)都有 pid 檢查,唯獨它沒有。
`EnumWindows` 列舉全桌面 top-level 視窗,且 window property **可跨行程移除**。
DLL 注入到兩個遊戲時,A 的 Shutdown 掃到 B 的視窗 → 因模組基址不同故 `cur == &SubclassProc` 為 false
→ 不還原**但仍移除 prop** → 在 B 身上觸發 A-1 的破壞。**修法**:補上與姊妹一致的 pid 過濾。

### A-3(= F2)🟠 `Shutdown()` 未重置 `g_hookInstalled` → 重啟後 keep-foreground 靜默半死 — ✅ FIXED

`Shutdown()` 呼叫 `MH_DisableHook` 卻沒重置 `g_hookInstalled`。之後 `SetKeepForeground(true)` 時
`if (!g_hookInstalled)` 為 false → **整個安裝區塊被跳過**,detour 仍是 disabled。
結果:UI 顯示已啟用、`IsKeepForegroundEnabled()` 回 1,但主要機制(`GetForegroundWindow` 幻覺)是死的,
只剩 WndProc subclass 路徑還有效。`Discrete_Shutdown` → `Discrete_Init` 循環即可觸發。

**修法**:`Shutdown()` 補 `g_hookInstalled = false`;安裝路徑改用新的 `CreateOrReuseHook()`,
把 `MH_ERROR_ALREADY_CREATED` 視為成功(Shutdown 只 disable 沒 remove,第一次安裝取得的 trampoline 仍有效)。

**驗證**:`build.cmd dll` SUCCESS(#1385,x64 + x86 + IL2CPP)。**待實機 smoke**:
勾選 keep-foreground → `Discrete_Shutdown` → `Discrete_Init` → 再勾選,確認 alt-tab 後遊戲仍持續執行
(A-3);開著 Steam overlay 之類的 overlay 再跑一次 shutdown,確認遊戲視窗仍正常回應(A-1)。

## 批次 B — proxy / injector(完成 2026-08-13,build #1391)

4 個 agent(每人一個子系統,自我對抗式驗證)。**7 CONFIRMED、1 REFUTED**,全數已修。

### B-1(= F45)🔴 winmm proxy 缺 export → **每一款 Unity 遊戲都開不起來** — ✅ FIXED

原宣稱是「某個共同載入的模組可能失敗」,實際嚴重得多。人工用 python 解 PE 匯入表獨立驗證:

- **`UnityPlayer.dll` 自己就靜態匯入 23 個 winmm 符號,proxy 只有 13 個沒漏 —— 缺 13 個**
  (整個 `waveIn*` 家族 + `waveOutGetDevCapsA/W` + `waveOutGetPosition`)。
- 抽樣 **6/6 個不同 Unity 版本的 UnityPlayer.dll,缺的完全是同一組**,非版本特例。
- 遊戲 .exe 靜態匯入 UnityPlayer.dll → loader 在**行程初始化**就綁定失敗 → 遊戲根本不啟動。

根因寫在 winmm.cpp 原註解裡:清單是從 **UnityPlayer.exe** 推導的,但現代 Unity 出的是
**UnityPlayer.dll**,後者多匯入 FMOD 的麥克風擷取路徑。

進一步掃 **14 款 Unity 遊戲、1536 個匯入 winmm 的模組**,補完 13 個後只剩一個未覆蓋:
`SDL2.dll` → `waveOutGetErrorTextW`(也已補)。**現在 x64/x86 兩份各 48 個 export,需求全滿足。**

**不能用 PE export forwarder 修**:forwarder 目標 `winmm.xxx` 會因遊戲目錄優先於 System32 而
轉回我們自己 → 無限遞迴。thunk 是必要的。又因 x86 是 stdcall(被呼叫方清堆疊),
每個 thunk 的參數個數必須與真實 export 一致,否則堆疊損毀 —— 已在檔頭寫明。

### B-2 🔴 proxy 解析路徑不可重入 + 可能呼叫空指標 — ✅ FIXED(使用者指出 timer re-entry)

`EnsureReal()` 在 winmm.cpp 與 version.cpp 兩份完全相同,三個問題:

1. **有界 spin 會過期**:輸掉 CAS 的執行緒跑 `for (i < 1000) Sleep(0)`;spin 用完 `g_real` 仍為 null
   → `ResolveExport` 回 nullptr → thunk 直接 `return fn args;` **呼叫空指標**,全程無 null 檢查。
2. **在 MM timer callback 裡阻塞**:`timeSetEvent` 的 callback 跑在高優先權 timer 執行緒,
   文件明訂不得阻塞,而 `timeKillEvent` 常常就是從該 callback 裡呼叫的。
3. `g_real` 是普通 `HMODULE`,跨執行緒讀寫無屏障。

而這整套機制**毫無必要**:`Proxy_LoadRealDll` 本身已由 SRWLOCK 序列化、依名快取、
並釋放輸家的重複 handle,`LoadLibraryW` 又是 refcounted —— 競爭的呼叫者本來就會收斂到同一個 handle。
改成 `std::atomic<HMODULE>` + 直接呼叫,**無 CAS、無 spin、無過期視窗、無可重入的東西**。

### B-3(= F49)DllMain 內 LoadLibraryW — agent 判 REFUTED,**但仍改掉了**

agent 的靜態分析認為風險不成立。但 UE5CEDumper(使用者指出的參考實作)的
`gen_proxy_forwarders.py` 檔頭有**實機證據**:在 DllMain 解析會在 host .exe 的靜態匯入
還在初始化時於 loader lock 下 LoadLibrary —— **這讓 Octopath Traveler 透過 dxgi proxy 當掉**。
實機當機紀錄勝過靜態論證。兩個 proxy 的 DllMain 都拿掉 `EnsureReal()`,改為 thunk 首次呼叫時
在遊戲執行緒上解析(DllMain 已返回),成本為零。

### B-4(= F48)🟠 ProxyInstaller 無所有權檢查 → 靜默摧毀第三方 DLL — ✅ FIXED

`version.dll` / `winmm.dll` 正是 ReShade / ENB / SpecialK / mod loader 用的檔名。
安裝時無條件 `File.Delete(otherPath)` + `File.Copy(overwrite: true)`;解除時無條件刪除四個檔名。
**後果比啟動失敗更糟**:我們的 proxy 會轉發所有 export,所以遊戲照常啟動、行為正常 ——
使用者的 mod 只是無聲消失,沒有錯誤、沒有備份可還原。

**關鍵是識別標記本來就存在,只是沒被查**:`version.rc.in:34` 對所有 Discrete 二進位檔寫死
`ProductName="Discrete"`,而 `ReadFileVersion` 已經在呼叫 `FileVersionInfo.GetVersionInfo()`,
只是丟掉了那個欄位。

**採保守預設**(如先前所述):新增 `IsOurDll()`,**無法證明是我們的就一律不碰**
(讀不到版本資源 → 視為他人的)。安裝:目標槽有他人 DLL → 拒絕並給明確訊息;
另一槽有他人 DLL → 留著不刪(兩者可共存,只有我們自己的兩個 proxy 互斥)。
解除:只刪能證明是我們的,並回報略過了哪些。

> 需另外決定備份檔遺失時的行為。

### B-5(= F46 / F47)inject-x86 — ✅ FIXED

- **F46**:timeout 路徑 `VirtualFreeEx(MEM_RELEASE)` 釋放的正是遠端執行緒 `LoadLibraryW` 的
  `lpParameter`。ntdll 用 `UNICODE_STRING` 包住呼叫者的緩衝區、直到名稱解析才複製,
  所以在活執行緒下解除映射會在 ntdll 內 fault → **遊戲死掉**,把「注入失敗」變成「掉了整個遊戲階段」。
  改為 timeout 時**刻意不釋放**(洩漏一頁,幾 KB),其餘錯誤路徑照舊釋放(執行緒未建立或已結束)。

  `D:\遊戲\...` 這種路徑會回報**假的「DLL not found」**。改用 `wmain(int, wchar_t**)`,
  UTF-16 從父行程的 `CreateProcessW` 一路原封不動送到 `WriteProcessMemory` —— 轉換整個消失。

### B-7(= F50)DllMain 下無界 join → 整個遊戲凍結 — ✅ FIXED(latent)

`PipeServer::Stop()` 的 `g_worker.join()` 無上限。worker 的 exit epilogue
(`_endthreadex` → `ExitThread` → `LdrShutdownThread`)必須取得 loader lock 才能跑各模組的

`DisableThreadLibraryCalls` 救不了(只擋我們自己的模組,走訪仍涵蓋 ucrtbase / UnityPlayer / mono)。

### C-1(= F53)🔴 `mono_enumImages` 用法錯誤 → fallback **會拋錯** — ✅ FIXED

```lua
function mono_enumImages(onImage)

```

我們寫 `local imgs = mono_enumImages()` → `onImage` 為 nil → 找到任何 image 就

### C-2(= F54)🔴 `Stream:read` 回傳 bytetable 而非 string → Mode-B bootstrap 第一個檔就死 — ✅ FIXED

### C-3(= F55)🟠 公開版 `registerSymbolBySignatureMatch` 缺全部防護 — ✅ FIXED

`discrete_*` 孿生(:546)有 `pcall(mono_method_getSignature, ...)` + `type(sig)=="string"` +

(「generic / uncompiled methods 會 throw 或回 nil」)。公開版(:239)**四道一個都沒有** →
只要目標 class 上**存在**這類 overload,`string.find(nil, ...)` 就中止整個 [ENABLE] 區塊;

### C-4(= F56)🟡 `[DISABLE]` 未重設 `DISCRETE_HAD_ERROR` — ✅ FIXED(**推翻上一輪 agent 的 REFUTED**)

### E-1(= F15)🔴 detached client worker 無例外屏障 → `std::terminate` 帶走遊戲 — ✅ FIXED

[PipeServer.cpp](../dll/src/shared/PipeServer.cpp) 每個 client 跑在 detached `std::thread` 上,

`Dispatch` 確實有包 handler(:156-161),但配置行為散落在保護範圍**之外**:

**修法**:整個 thread body 包 `try/catch(...)`。掉一個 client 遠好過殺掉遊戲。

### E-2(= F23)🟠 disconnect hook 每次 Shutdown→Init 循環累加 — ✅ FIXED

`Discrete_Init` 以 `g_initialized` CAS(false→true)守衛並註冊 GC-drain hook,
但 `Discrete_Shutdown` 用 `exchange(false)` **重置該 latch** → 再次 `Init` 會**再註冊一個**;
`g_disconnectHooks` 只有 `push_back`,全 repo 無任何清除。
結果:**每次** client 斷線都跑 N 次完整 GC collection(docs 記載單次 ~100 ms)。
記憶體成長可忽略,**時間成本才是傷害**。
**修法**:新增 `PipeServer::ClearDisconnectHooks()`,在 `Stop()` 尾端呼叫(與 Init 的註冊配對)。

### E-3(= F22)🟠 session 在 client 斷線後無限期滯留 — ✅ FIXED(**嚴重度低於原宣稱**)

原宣稱「never dropped → high memory-leak」。事實核對:`DropAll()` 確實**零呼叫點**,
但 `ExpireOldSessions()`(5 分鐘 idle)會在**每次 `Begin()`** 時執行,所以這不是無界成長 ——
是**滯留**:client 斷線(或強制結束)後,若再也沒有新的 `Begin`,
它斷線當下持有的 session 會留到行程結束。一份 snapshot plan 是數十 MB,
在 32-bit 遊戲裡白佔這麼多是實在的代價。

**修法**:註冊一個 hook,在**最後一個** client 離開時 `DropAll()` 三個 manager。
**必須 gate 在「最後一個」** —— session 沒有 owner id,而最多 4 個並行 client,
無條件 drop 會摧毀其他 client 的 session。disconnect hook 內呼叫者仍計入自己,故 `== 1` 即為最後一個。
殘留競態(該窗口內新 client 剛 begin 的 session 會被清掉 → 重跑一次)
與 ScanCancel 已文件化的 collateral-cancel 取捨同性質,遠低於它預防的滯留成本。

### E-4(= F17)🟡 `Stop()` 未 arm scan cancel → drain 必定逾時 — ✅ FIXED

`Stop()` 設 `g_running=false` + `SetEvent`,然後 400×5 ms 等 `g_activeClients` 歸零。
但正在跑數分鐘掃描的 worker 不看這兩者 —— 它輪詢的是 `ScanCancel`,而 `Stop()` 從未 arm。
所以 drain **必定**燒完 2 秒後放棄。**修法**:`Stop()` 開頭呼叫 `ScanCancel::RequestCancel()`。
這同時大幅降低 E-5 的觸發機率。

### E-5(= F24)🟠 `g_stopEvent` 在 worker 仍存活時被關閉 → 空轉 / use-after-close — ✅ FIXED(**推翻上一輪 REFUTED**)

上一輪以「monitor 早在 handle 關閉前就結束」駁回。該前提**只在 client 於 2 秒 drain 內完成時成立**。
長掃描正是不成立的情況:

1. `Stop()` 2 秒 drain 逾時放棄 → `CloseHandle(g_stopEvent)` + 設 `nullptr`。
2. monitor 執行緒仍活著(其 client 還在掃描),下一輪 `WaitForSingleObject(nullptr, 150)`
   回 **`WAIT_FAILED` 且立即返回** —— 不是 `WAIT_OBJECT_0` 所以不 break,`monitorStop` 也還是 false。
3. → **無 sleep 的緊密迴圈**,整個掃描期間 100% 吃掉一核。
4. 更糟:handle 值若被系統重用,那是對**無關核心物件**的 use-after-close。

**修法(兩層)**:(a) monitor 快照 handle,並把「非 WAIT_OBJECT_0 且非 WAIT_TIMEOUT」一律視為
「sleep 150 再檢查」,絕不空轉;(b) `Stop()` **只在 drain 真的成功(`g_activeClients == 0`)時**
才關閉 event,否則刻意洩漏這一個 handle 並記 log —— 一個 HANDLE 遠比那個競態便宜,
且 `Start()` 若重啟會配置新的。

**驗證**:`build.cmd dll` SUCCESS(#1393,x64 + x86 + IL2CPP);`DropAll()` 由 0 個呼叫點變成 3 個。
純 C++ 未動 C#。**待實機 smoke**:大型 snapshot 後關閉 UI,確認遊戲記憶體回落(E-3);
掃描中途關閉 UI,確認 DLL 停止且無單核 100%(E-4/E-5)。

## 批次 H — shared infra（完成 2026-08-13）

### H-1（= F40）🔴 AOB 解碼器漏掉 group 3 的 immediate → 指令流失步 — ✅ FIXED

[AobPattern.cpp](../dll/src/shared/AobPattern.cpp) `Lookup()`：

```cpp
if (op == 0xF6) { o.hasModRm = true; return o; }   // group 3 byte (sub-op imm decoded later)
if (op == 0xF7) { o.hasModRm = true; return o; }   // group 3 word/dword
```

註解自己寫著「decoded later」—— **但沒有任何地方 later 去解**。
Group 3 的 immediate 取決於 ModRM.reg 子運算碼：`reg=0/1` 是 `TEST r/m, imm`（F6 帶 imm8、F7 帶 imm16/32），
`reg=2..7`（NOT/NEG/MUL/IMUL/DIV/IDIV）沒有。

所以 `F7 /0` 少算 **4 bytes**、`F6 /0` 少算 1 byte → 解碼器從指令中途繼續 →
**該視窗內後續每一個指令邊界都是錯的** → 產出的 AOB wildcard 位置全錯，掃不到（或更糟，掃到別的東西）。
AOB 是使用者可見輸出（`Copy: aobscan`）。

**修法**：因為取決於 ModRM.reg，修正必須放在 ModRM 解出之後（`DecodeOne` 內），
以 `opLen == 1` 守衛避免誤觸 `0F`-escaped opcode（與既有 B8-BF REX.W 規則同一寫法）。

**姊妹檢查（照批次 D/G 教訓）**：其餘帶 immediate 的 group ——
`0x80/0x81/0x83`（group 1）、`0xC0/0xC1`（group 2）、`0xC6/0xC7`（group 11）——
**都已正確設定 `immSize`**，因為它們不取決於 ModRM.reg。這次沒有姊妹。

**手動驗算**（DLL 端無測試套件）：
`F7 C0 01 00 00 00`（`test eax,1`）2→**6** ✓；`F7 D0`（`not eax`）2→2 ✓；
`F6 C3 05`（`test bl,5`）2→**3** ✓；`48 F7 E1`（`mul rcx`）3→3 ✓。
`66` 前綴把 F7 的 imm 降為 2、REX.W 不提升 TEST 的 imm —— 兩者都由既有邏輯正確處理。

### H-2（= F41）🟠 `EnumerateModules` 讀出固定陣列尾端 — ✅ FIXED

```cpp
HMODULE mods[1024];
::EnumProcessModules(proc, mods, sizeof(mods), &cbNeeded);
DWORD count = cbNeeded / sizeof(HMODULE);
for (DWORD i = 0; i < count; ++i) { ... mods[i] ... }
```

`cbNeeded` 是「存放**全部** module handle 所需的位元組數」，**不是實際寫入數**（MSDN 明載：
cbNeeded > cb 時要放大陣列重呼叫）。模組數 > 1024 時 `count > 1024`，迴圈就讀
`mods[1024..count-1]` —— **stack 陣列尾端之外**，把垃圾 HMODULE 餵給
`GetModuleBaseNameW` / `GetModuleInformation`。
**修法**：改用 `std::vector` 依 `cbNeeded` 成長重試（API 的正規用法），並保留一道 clamp。

### H-3（= F42）🟠 `NtQueryInformationThread` 的 lazy init 有競態 → 靜默跳過 thread-stack 過濾 — ✅ FIXED

```cpp
static NtQueryInformationThreadFn cached = nullptr;
static bool tried = false;
if (!tried) { tried = true; ... cached = GetProcAddress(...); }
```

兩個 static 都是 constant-initialised，所以編譯器**不會**產生 thread-safe guard。
A 執行緒設 `tried = true` 後、指派 `cached` **之前**被搶佔 → B 看到 `tried == true`
就帶走 **nullptr** → 呼叫端解讀為「此 OS 無法回報 thread stack」→
**該次掃描的 thread-stack 過濾全部靜默失效**，stack 記憶體被當成 heap 掃描。
兩個 client 同時開始第一次掃描即可觸發。
**修法**：改用動態初始化的 function-local static（C++11 保證只初始化一次且其他執行緒會等待）。

**驗證**：`build.cmd dll` SUCCESS（x64 + x86 + IL2CPP）。純 C++，未動 C#。
**待實機 smoke**：`Copy: aobscan` 產出的 pattern 應能掃到（H-1，尤其目標附近有 `test` 指令時）。
